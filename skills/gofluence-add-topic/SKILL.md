# Add a GoFluence topic to the handbook

The handbook is a Docusaurus section (`docs/gofluence-handbook/`) with one `.mdx` page per class topic, grouped in five folders. Every page follows the same 9-section template so review stays predictable. The user pastes raw class notes; your job is to turn them into a finished page in the right place with no manual steps left.

Read `references/conventions.md` first (group table, front matter, tags, components, MDX rules) and copy the structure from `references/template.mdx`. For a feel of the finished style, open one existing page, e.g. `docs/gofluence-handbook/01-grammar/zero-conditional.mdx`.

Run every command from the repo root.

## Workflow

1. **Parse the paste.** Find the topic title (keep the English wording as given), the rules, example sentences and vocabulary. Ignore platform noise such as "Learn", "Practice", "Summary", step numbers and menu text. If the paste has no clear title, derive one from the content and say so.

2. **Save the source (only if the file exists).** If `gofluent.md` is at the repo root, append the raw paste after a blank line so the user's source notes stay complete; skip it if the same title is already there. If the file does not exist, do not create it: the handbook page is the record.

3. **Check for duplicates.** `grep -rh '^title:' docs/gofluence-handbook/0*/` and compare with the new title (case-insensitive, ignoring "How to"). If the topic already exists, update that page with the new material instead of creating a second one, and tell the user.

4. **Pick the group** with the decision table in `references/conventions.md`. If nothing fits, ask the user before creating a new group folder.

5. **Choose slug and position.** Kebab-case slug, no leading "How to". `sidebar_position` is the highest value in that folder plus one (command in `conventions.md`).

6. **Write the page** at `docs/gofluence-handbook/<group>/<slug>.mdx`:
   - All nine sections, exact headings, in order. Short B1-B2 sentences.
   - `description` is one sentence of what the learner can do after the topic ("Use X to..."), not a copy of the pasted summary. Keep the pasted example sentences verbatim somewhere in the page; extra examples are welcome.
   - Build the content from the pasted notes; fill gaps with standard English grammar and record that in a `:::info Assumptions` block. The user is a Spanish speaker, so give Spanish hints in the vocabulary table and add a Spanish-speaker pitfall where one exists.
   - Use at least two of Tabs, titled code blocks, `Dialogue` in the workplace examples; add `Quiz` when a multiple-choice check fits.
   - 6-12 `VocabTable` rows. The glossary is generated from these rows, so keep the keys `en`, `meaning`, `example` with plain string values.
   - If you need a tag that is not in `docs/tags.yml`, add it there first.
   - Add 0-3 relative `.mdx` links to existing related pages only when they help the learner.

7. **Regenerate the glossary.** `python3 -I skills/gofluence-add-topic/scripts/build_glossary.py`

8. **Verify.**
   - `python3 -I skills/gofluence-add-topic/scripts/check_topic.py docs/gofluence-handbook/<group>/<slug>.mdx` and fix whatever it reports.
   - `bun run build --locale en`. Fix MDX errors and broken links. If the output lists broken links to files that exist, the Docusaurus cache is stale: run `bun run clear` and build again.

9. **Report** in a few lines: file path, group and position, glossary entry count (from step 7), and any assumptions you made. Do not commit unless the user asks.

## Why these rules
- Numbered, fixed H2 headings keep every page scannable and let `check_topic.py` catch a forgotten section.
- Tags must exist in `docs/tags.yml`; otherwise Docusaurus warns and the tag page is missing.
- A bare `<`, `{` or `}` breaks MDX compilation, so quote such characters in backticks.
- The sidebar is autogenerated from the folder, so no config change is needed when you add a page.
- The glossary is a generated file; never edit `glossary.mdx` by hand.
